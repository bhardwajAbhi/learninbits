In one line

Most security bugs in Android apps come from a small number of habits. Change these habits and you close most of the doors.

Security reports about Android apps show the same mistakes again and again. An activity is open to all apps. A secret key is in the APK. A token is in the log. Each mistake is small, and each mistake is easy to prevent.

This article gives you ten habits. Each habit has a short reason, a wrong example and a correct example. The examples use Kotlin and the Android manifest.

Who attacks your app?

Before you write secure code, know who can attack. For a normal Android app, there are four types of attacker:

  • A different app on the same phone. It can send intents to your app and read files that your app shares.
  • A person on the same network. For example, on public Wi-Fi. This person can read data that your app sends without encryption.
  • A person with the phone or with a backup. This person can read data that your app stores without protection.
  • A person with your APK. Any person can download your APK and read the code. Code obfuscation makes this slower, but it does not stop it.

Keep these four attackers in mind for each habit.

1. Do not export components without a reason

An exported activity, service, receiver or provider is open to all apps on the phone. Export a component only when a different app must start it. Since Android 12, you must set android:exported on each component that has an intent filter. Set it to false when you are not sure.

Wrong

<activity
  android:name=".AdminActivity"
  android:exported="true" />

Correct

<activity
  android:name=".AdminActivity"
  android:exported="false" />

2. Protect the components that you export

Sometimes a different app must start your component, for example your second app. Then export the component and add a permission with the signature protection level. Android gives this permission only to apps that you signed with the same key.

<permission
  android:name="com.example.app.permission.SYNC"
  android:protectionLevel="signature" />

<service
  android:name=".SyncService"
  android:exported="true"
  android:permission="com.example.app.permission.SYNC" />

3. Treat all input as untrusted

Intents, deep links, files and data from a server can come from an attacker. Examine each value before you use it. Make a list of the values that you accept. Refuse all other values.

Wrong

val url = intent.data
  ?.getQueryParameter("url")
webView.loadUrl(url!!)

Correct

val uri = intent.data
  ?.getQueryParameter("url")
  ?.let(Uri::parse)
if (uri?.scheme == "https" &&
    uri.host == "www.example.com") {
  webView.loadUrl(uri.toString())
}

4. Use explicit intents and immutable PendingIntents

An implicit intent goes to any app that says that it can do the action. A different app can catch it. When you send data to a component in your own app, name the component. When you give a PendingIntent to a different app, make it immutable. Then the other app cannot change it.

val intent = Intent(context, ReminderReceiver::class.java)
val pending = PendingIntent.getBroadcast(
  context, 0, intent, PendingIntent.FLAG_IMMUTABLE
)

5. Use parameters in database queries

If you join user text into an SQL string, an attacker can change the query. This attack has the name SQL injection. It is a risk in content providers that other apps can call. Use a ? for each value and give the values separately.

Wrong

db.rawQuery(
  "SELECT * FROM notes WHERE title = '$title'",
  null)

Correct

db.rawQuery(
  "SELECT * FROM notes WHERE title = ?",
  arrayOf(title))

6. Keep secrets out of the APK

Any person can open your APK and find a string in it. An API key in the code or in strings.xml is not secret. Keep server secrets on your server. For keys that must be on the phone, use the Android Keystore. The Keystore keeps the key in protected storage, and on many phones in secure hardware. Your app can use the key, but it cannot read the key.

val generator = KeyGenerator.getInstance(
  KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
generator.init(
  KeyGenParameterSpec.Builder(
    "notes_key",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .build())
val key = generator.generateKey()

7. Store private data in private places

Files in the internal storage of your app (context.filesDir) are private to your app. Files in shared storage are not. Keep personal data in internal storage, and encrypt very sensitive data with a Keystore key.

Backups are a second path out of the phone. Remove session tokens and similar files from backups. On Android 12 and higher, use data extraction rules:

<!-- res/xml/data_rules.xml -->
<data-extraction-rules>
  <cloud-backup>
    <exclude domain="sharedpref" path="session.xml" />
  </cloud-backup>
  <device-transfer>
    <exclude domain="sharedpref" path="session.xml" />
  </device-transfer>
</data-extraction-rules>

Then add android:dataExtractionRules="@xml/data_rules" to the <application> element.

8. Send data only over HTTPS

A person on the same network can read and change HTTP traffic. Since Android 9, apps cannot use clear text traffic by default. Keep this setting. Write it in a network security configuration, so that a library or a later change cannot turn it on by accident.

<!-- res/xml/network_security_config.xml -->
<network-security-config>
  <base-config cleartextTrafficPermitted="false" />
</network-security-config>

9. Lock down WebView

A WebView is a full browser inside your app. If it shows a page from an attacker, that page can attack your app. Give the WebView only the features that the page needs. Do not connect Java or Kotlin objects to JavaScript with addJavascriptInterface on pages that you do not control.

webView.settings.apply {
  javaScriptEnabled = false   // set to true only if the page needs it
  allowFileAccess = false
  allowContentAccess = false
}

10. Keep personal data out of logs

Logs are easy to collect. A bug report from a user, a test device or a crash tool can copy them. Never write tokens, passwords or personal data to the log.

Wrong

Log.d("Login", "token=$token")

Correct

Log.d("Login", "Login complete")
Security lens

Look at your own app the way an attacker does. Open the release APK, not the source code. Find each exported component, each permission and each string that looks like a key or a URL. Tools like APK Inspector show this information in one window.

Do this check before each release. A new library can add exported components or permissions that you did not write.

Try it yourself

Find the exported components in an APK. You need aapt from the Android SDK build tools.

# Show the manifest and find the exported components
aapt dump xmltree app-release.apk AndroidManifest.xml | grep -B 3 exported

# Show only the log lines of your app
adb logcat --pid=$(adb shell pidof -s com.example.app)

Key terms

Exported
A component that other apps can start.
Intent
A message that asks for an action, for example to open a screen.
PendingIntent
An intent that you give to a different app to send later.
Keystore
The Android system that keeps keys safe from the app and from attackers.
SQL injection
An attack that changes a database query through user input.
