In one line

A chain joins several steps into one, so that the output of each step goes into the next and one call runs the whole task.

What you will learn

  • Why a task with several steps is easier to build as a chain
  • How the pipe symbol | joins a prompt, a model and a parser
  • How to join two chains, so that the answer of the first becomes the input of the second
  • How to see what each step receives and returns, with the debug mode

Read chapter 5 first. In this chapter, you will turn the template and the model from that chapter into a chain.

The idea

In chapter 5, your code did each step by hand. It filled the template with format(), sent the prompt with invoke() and took the text with .content. For one step, this is fine. A real task often has several steps, such as first sorting a description into categories and then writing a report about them.

The LangChain Expression Language (LCEL) joins such steps with the pipe symbol |. The output of the step on the left goes into the step on the right. The result is a chain, and a chain has the same invoke() method as a model. One call then runs all the steps in order, so that your code stays short and each step stays easy to change.

A typical chain has three steps. The prompt template fills its slots. The model writes the answer. An output parser turns the answer into the form that the next step needs, such as plain text.

Real-life analogy

A chain works like an assembly line in a factory. Each station does one job and passes the part to the next station. You can add a station or replace one, and the rest of the line stays the same.

What you will build

You will build a page that analyzes a description of how an app behaves. The first chain maps the behavior to techniques in the MITRE ATT&CK Mobile matrix. This matrix is a public list of known attack techniques, each with an ID. The second chain writes a short threat report from that mapping. One click runs both chains.

The same structure works for any two-step task, such as summarizing a document and then translating the summary. You will change only the two templates.

Build it step by step

Step 1Create the file

In the code folder, create the folder 06_lang_chain_expression_language_LCEL and in it the file app_ollama.py.

Step 2Import the libraries

from langchain_ollama.chat_models import ChatOllama
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.globals import set_debug

import streamlit as st
  • StrOutputParser is new. It takes the answer of the model and returns only its text, so that the next step receives plain text and not a message object.
  • set_debug is new. It turns the debug mode of LangChain on or off.
  • ChatOllama, PromptTemplate and streamlit are the same as in chapter 5.

Step 3Turn on the debug mode and load the model

set_debug(True)

llm = ChatOllama(model="gemma:2b")
  • set_debug(True) makes LangChain print each step of a chain to the terminal, with its input and its output. When a chain gives a strange result, you can then see which step caused it.
  • llm uses gemma:2b, as in chapter 5.

Step 4Write the first template

mitre_prompt = PromptTemplate(
    input_variables=["behavior"],
    template="""
    You are a senior Android Malware Analyst with 15 years of experience in the domain.
    Analyze the following observed Android malware behavior.
    {behavior}

    Your task is to map the behavior ONLY to the MITRE ATT&CK Mobile Matrix (Android platform).

    For every matching technique, provide:
    - Technique ID
    - Technique Name
    - One-line justification
    """
)
  • The template has one slot, {behavior}, for the text that the user types.
  • "ONLY to the MITRE ATT&CK Mobile Matrix" limits the model to one list of techniques, so that the answer uses known IDs and names.
  • The three items under "For every matching technique" fix the form of each result, so that the second step always gets the same kind of input.

Step 5Write the second template

report_prompt = PromptTemplate(
    input_variables=["techniques"],
    template="""
    You are a Mobile Threat Intelligence Analyst.

    Below are the mapped MITRE ATT&CK Mobile techniques.
    {techniques}

    Generate a professional Android Threat Intelligence Report.

    Include the following sections:

    1. Executive Summary

    2. Mobile ATT&CK Techniques

    3. Possible Malware Objectives

    4. Detection Opportunities

    5. Mitigation Recommendations

    Keep the report concise, clear and easy to understand.
    """
)
  • The slot {techniques} will receive the output of the first chain.
  • The five numbered sections fix the structure of the report, as the numbered list did in chapter 5.

Step 6Build the chains

first_chain = mitre_prompt | llm | StrOutputParser()

second_chain = report_prompt | llm

overall_chain = first_chain | second_chain
  • mitre_prompt | llm | StrOutputParser() is the first chain. The template fills its slot and the model answers. The parser then keeps only the text.
  • report_prompt | llm is the second chain. It has no parser, so it returns the full message. The page will use .content.
  • first_chain | second_chain joins the two chains. The text from the first chain goes into the second. The second template has only one slot, so LangChain puts the text into {techniques} by itself.
  • These lines only describe the chains. Nothing runs until the code calls invoke().

Step 7Build the page

st.set_page_config(page_title="Android Mobile ATT&CK Mapper", page_icon="🤖")

st.write(
    "Describe the observed Android malware behavior. "
    "This application will first map the behavior to the **MITRE ATT&CK Mobile Matrix**, "
    "then generate a threat intelligence report."
)

behavior = st.text_area(
    label="Observed Android Malware Behavior",
    height=400, 
    placeholder="""

    App uses following permissions:
    READ_SMS
    INTERNET
    RECEIVE_BOOT_COMPLETED

    Observed Behaviour:
    - Reads incoming OTP SMS messages
    - Starts automatically after device reboot
    - Sends collected SMS messages to a remote server
    - Requests SMS permissions during installation
    - Hides app icon from the app drawer
    """
)
analyze_button = st.button(label="Analyze Behavior",)
  • page_icon sets the small icon on the browser tab.
  • st.write shows a short description at the top, so that the user knows what to type.
  • st.text_area is a text box with many lines, so that the user can paste a long description. placeholder shows an example in gray, and height=400 makes the box tall enough for it.

Step 8Run the chain

if analyze_button:
    if behavior.strip():
        with st.spinner(text="Analyzing malware behavior..."):
            response = overall_chain.invoke({"behavior":behavior})
        st.subheader("Threat Intelligence Report")
        st.write(response.content)
    else:
        st.warning("Please enter the observed Android malware behavior.")
  • behavior.strip() removes spaces and empty lines, so that a box with only spaces counts as empty.
  • overall_chain.invoke({"behavior": behavior}) runs both chains with one call. The key "behavior" must match the slot of the first template.
  • st.write(response.content) shows the report. The output of the first chain is not on the page, but the debug mode prints it in the terminal.

streamlit run code/06_lang_chain_expression_language_LCEL/app_ollama.py

Streamlit will start a small web server and print its address.

Open the Local URL in your browser. Paste the example from the gray text in the box, with the app details, the permissions and the observed behavior. Then click Analyze Behavior. The report will appear after both chains finish, so it takes longer than in chapter 5.

Your output can be different

A language model does not always give the same answer. Your report can name other techniques. The sections of the report will be the same, because the second template asks for them.

The parts of a line

Every block starts with one line, and each line has the same parts. Once you can read one line, you can read the whole output.

PartExampleWhat it tells you
Event[chain/start]
[llm/end]		Whether a step starts or ends. llm marks a call to the model, and chain marks every other step. In the terminal, start lines are green and end lines are cyan, so that you can scan the output quickly.
Path[... > llm:ChatOllama]Where the step sits. The full path reads from left to right, like a folder path. The whole chain, chain:RunnableSequence, comes first, and the step inside it comes after the > sign. Each step shows its kind and its class, so that you can match it to one part of your code.
Time[9.84s]How long the step took. Only end lines carry a time. It shows you which step makes the app slow.
DataThe JSON below the lineWhat the step received or returned. Some steps show only [inputs] or [outputs], because LangChain prints the full data only when it is a plain dictionary.

The times already tell a story. The two prompts and the parser take a millisecond or less. The two model calls take almost all of the 31 seconds. If the app feels slow, a faster or smaller model helps, and changes to the rest of the chain do not.

The line to check first

The most useful block is the input of the model, under [llm/start]. The prompts list shows the exact text that reached the model, after the template filled in its slot. Human: marks the role of the message, and \n marks a line break. When an answer looks wrong, read this text first. A missing value, an empty slot or a mistake in the template will show up here, before the model even starts.

The end of the model call, under [llm/end], holds the answer in text. Further down, usage_metadata counts the tokens. input_tokens counts the prompt, and output_tokens counts the answer. More tokens make a call slower, and with a paid model such as GPT or Gemini, they also make it cost more.

Follow the data through both chains

The debug output lets you follow one piece of data from the page to the report. The behavior from the text box enters the whole chain and the first prompt. The answer of the first model call passes through the parser and comes out as {"output": "..."}. The second prompt then receives the same text. The debug mode labels a plain text input as input, and the template puts it into its only slot, {techniques}. The second model call writes the report, and the whole chain ends.

The page never shows the techniques from the first chain. In the terminal, they are right there, between the two chains. The next section shows why that matters.

Look closely

The report looks professional, but its technique IDs are wrong. T1011 is "Exfiltration Over Other Network Medium" in the Enterprise matrix, not a mobile technique. T1015 is "Accessibility Features", also from the Enterprise matrix. "Lateral Movement" is the name of a tactic, which is a group of techniques. It is not the name of one technique.

The Mobile matrix has techniques for this app. Examples are T1636.004, SMS Messages and T1628.001, Suppress Application Icon. The second chain trusted the first chain completely and built the whole report on its mistakes.

This is the main risk of a chain. An error in an early step travels to every later step. The debug output helps here. It shows the techniques between the two chains, so that you can check them before you trust the report.

Security lens

Each step of a chain trusts the output of the step before it. A wrong technique ID or an invented fact in step one becomes a confident claim in the final report. Check the output of the first step against the real source, such as the MITRE ATT&CK Mobile matrix, before you use a report. Also, the debug mode prints every prompt and answer in the terminal. Turn it off in an app for real users, so that private data does not end up in logs.

Check yourself

What does StrOutputParser() do at the end of the first chain?

It takes the answer of the model and returns only its text, so that the second chain receives plain text.

How does the text from the first chain reach the slot {techniques}?

The pipe symbol passes the text to the second chain. The second template has only one slot, so LangChain puts the text into it.

The report has a wrong technique ID. Where do you look first?

At the output of the first chain, which the debug mode prints in the terminal. The error usually starts there.
