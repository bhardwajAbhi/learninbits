Program of thought lets the model write a small program for a problem, and the computer runs that program to get the exact answer.

The idea

A language model predicts text, one piece at a time. It does not calculate. For a short sum, the most likely next text is usually the correct number. For a long chain of multiplications, percentages and unit conversions, the most likely text is often only close. The reasoning reads well, and the final number is still wrong. Chapter 12 showed exactly this effect with Qwen.

Program of thought (PoT) splits the work in two. The model does what it is good at. It reads the problem, plans the steps and writes them as a short program. The computer then runs the program and computes the exact result. The model never has to produce the final number itself. The program can be in any language, and this course uses Python, because all its examples are in Python.

The method comes from research in 2022. The paper "Program of Thoughts Prompting" by Chen and others showed large gains on numerical questions when the model wrote code instead of text. A related method from the same year, Program-Aided Language models (PAL) by Gao and others, follows the same idea.

Real-life analogy

An experienced analyst does not add 40 invoice lines in her head. She opens a spreadsheet, types the numbers and writes one formula, such as =SUM(B2:B41)*1.18. Her skill lies in choosing the right formula. The spreadsheet does the arithmetic without error. Program of thought gives the model the role of the analyst and gives Python the role of the spreadsheet.

Step 3Find the code in the reply

The model answers with text, an explanation followed by a fenced code block. The first job of your program is to cut the code out of that text.

def extract_and_run_code(response: str) -> str:
    """Extract Python code from the response and execute it, capturing
    whatever the code prints to stdout."""

    # Find the fenced code block in the model's response
    code_match = re.search(r"```python\n(.*?)```", response, re.DOTALL)
    if not code_match:
        return f"No code found. Raw response:\n{response}"

    code = code_match.group(1)
  • re.search(pattern, response, re.DOTALL) looks for the first place in response where the pattern fits.
  • ```python\n matches the opening fence, three backticks, the word python and a line break.
  • (.*?) is a group that captures any text. The ? makes it lazy, so it stops at the first closing fence instead of the last one.
  • ``` at the end matches the closing fence.
  • re.DOTALL lets the dot match line breaks too. Without it, the group can only capture a single line.
  • code_match.group(1) returns the text of the first group, the code without the fences.
  • If nothing matches, the function returns the raw reply, so that you can see what the model wrote instead.
A regular expression in one sentence

A regular expression is a small pattern language for text. ```python\n(.*?)``` reads as "an opening python fence, then any text that you keep, then a closing fence".

Step 4Run the code and capture what it prints

The prompt asks the model to print the final answer. print() normally writes to the terminal, where your program cannot read it. The trick is to point sys.stdout to a buffer for a moment.

    # Execute the extracted code and capture its printed output
    try:
        # Save the real stdout, then point it to an in-memory buffer
        old_stdout = sys.stdout
        sys.stdout = buffer = io.StringIO()

        exec(code, {"__builtins__": __builtins__})

        # Read what the code printed, then restore the real stdout
        output = buffer.getvalue()
        sys.stdout = old_stdout
        return f"CODE:\n{code}\n\nOUTPUT:\n{output}"
    except Exception as e:
        return f"Error executing code: {e}\n\nCODE:\n{code}"
  • old_stdout = sys.stdout keeps a reference to the real output stream, so that you can restore it.
  • sys.stdout = buffer = io.StringIO() creates an empty buffer and makes it the new output stream. Every print() now writes into the buffer.
  • exec(code, {"__builtins__": __builtins__}) runs the code string as Python. The dictionary is the global scope of that code. It holds only the built-in functions, so the model's code does not see the variables of your program.
  • buffer.getvalue() returns everything that the code printed, as one string.
  • sys.stdout = old_stdout puts the real stream back, so your own print() calls reach the terminal again.
  • The except branch catches any error in the model's code and returns the message with the code.

Step 5Spot the hidden bug

Read Step 4 again and follow the path of an error. Suppose the model's code divides by zero. exec() raises ZeroDivisionError, and Python jumps straight to the except branch. The line sys.stdout = old_stdout never runs.

From that moment on, sys.stdout still points to the buffer. The function returns its error message, and your loop prints it, into the buffer. Every later print() of your program disappears without a trace. The program keeps running, but the terminal stays silent. This kind of bug is hard to find, because nothing crashes.

The file already contains the fix. It sits in the comments under the function of Step 4. Without the # signs, it reads as follows.

from contextlib import redirect_stdout

def extract_and_run_code(response: str) -> str:
    code_match = re.search(r"```python\n(.*?)```", response, re.DOTALL)
    if not code_match:
        return f"No code found. Raw response:\n{response}"

    code = code_match.group(1)

    try:
        buffer = io.StringIO()
        with redirect_stdout(buffer):
            exec(code, {"__builtins__": __builtins__})

        output = buffer.getvalue()
        return f"CODE:\n{code}\n\nOUTPUT:\n{output}"
    except Exception as e:
        return f"Error executing code: {e}\n\nCODE:\n{code}"
  • redirect_stdout(buffer) from the contextlib module points sys.stdout to the buffer for the length of the with block.
  • When the block ends, Python restores the real stream. This also happens when the code inside the block raises an error.
  • The rule behind it is general. Whenever you change a global state for a moment, use a with block or try and finally, so that the restore step always runs.
Before and after

With the first version, one failing code block silences the rest of the run. With redirect_stdout, the failing block returns its error, and the next problem prints normally. Example 2 avoids the issue in another way, because it never redirects output at all.

import re

from dotenv import load_dotenv

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser


def extract_and_run_code(response: str) -> str:
    """Extract Python code from the response and execute it, reading the
    final answer from a variable instead of capturing printed output."""

    # Find the fenced code block in the model's response
    code_match = re.search(r"```python\n(.*?)```", response, re.DOTALL)
    if not code_match:
        return f"No code found. Raw response:\n{response}"

    code = code_match.group(1)

    # Execute the extracted code and read the answer variable directly
    try:
        namespace = {}
        exec(code, {"__builtins__": __builtins__}, namespace)

        if "answer" not in namespace:
            return f"No 'answer' variable found.\n\nCODE:\n{code}"

        answer = namespace["answer"]
        return f"CODE:\n{code}\nANSWER: {answer}"
    except Exception as e:
        return f"Error executing code: {e}\n\nCODE:\n{code}"

When it works and when it does not

  • It works for any question with an exact answer and a formula behind it. Examples are counts, rates, costs, durations, dates and unit conversions.
  • It does not help with questions of judgment, such as "Is this log entry suspicious?" No formula decides that. Use the reasoning patterns of chapters 8 to 12 there.
  • The formula can still be wrong. Python computes exactly what the code says. If the model misreads the problem, the code is wrong and the result is exactly wrong. Read the code once, or test it with a case whose answer you know.
  • The reply can have no code. A model sometimes answers in words only. extract_and_run_code() then returns "No code found" with the raw reply.
  • The fence can differ. The pattern needs exactly ```python and a line break. A reply with ```Python, ``` python or ```py slips through. A more tolerant pattern helps.

Security lens

Both examples run code that a model wrote, with exec(), inside your own program and with all the rights of your own program. That code is untrusted input, just like text from a web form.

  • The model follows the input. A problem text can contain a hidden instruction. The model can then write code that does something else, such as reading your .env file with its API keys or running a shell command. This is prompt injection, and with exec() it turns into code execution on your machine.
  • Mistakes are risks too. Even without an attacker, a model can write an endless loop or code that deletes a file by accident.
  • Treat the two examples as learning demos. They show the method clearly. Do not run them on problems from users or from the internet.

An empty builtins dictionary is not enough

A first idea is to hide the dangerous functions. exec(code, {"__builtins__": {}}) runs the code without open, __import__ and every other built-in function. It looks safe, but it is not.

Every Python object knows its class, and every class knows its parent classes. Code such as ().__class__.__bases__[0].__subclasses__() starts from an empty tuple, climbs to the base class object and lists every class in memory. Some of those classes lead back to modules such as os. Python's own documentation warns that exec() is not a security boundary. Hiding names inside the same process does not build a wall.

Three walls

The safe files add three independent walls. Each one stops different attempts, and together they cover much more than any single one.

  1. A check before anything runs. Python's ast module reads the code as a syntax tree, a structure of statements and expressions, without running it. A short function walks the tree and rejects anything that a calculation never needs.
  2. A separate Python process. The code runs in a new Python process, started with subprocess.run(), not with exec() inside your program. A crash or a trick in that process cannot touch the variables, the keys or the output stream of your program.
  3. Limits on that process. A timeout stops endless loops. An empty environment hides your API keys. An empty temporary folder means that relative file paths reach nothing. Python's isolated mode ignores user settings and user packages.

Part 3Check the code with the syntax tree

def check_code(code: str) -> None:
    """Read the code as a syntax tree (without running it) and raise
    ValueError if it uses anything outside our small safe set."""

    tree = ast.parse(code)

    for node in ast.walk(tree):
        # 1. Only allow imports from the allowlist
        if isinstance(node, ast.Import):
            names = {alias.name.split(".")[0] for alias in node.names}
        elif isinstance(node, ast.ImportFrom):
            names = {(node.module or "").split(".")[0]}
        else:
            names = set()

        blocked = names - ALLOWED_IMPORTS
        if blocked:
            raise ValueError(f"Import not allowed: {', '.join(sorted(blocked))}")

        # 2. Block risky built-in functions such as open() or eval()
        if isinstance(node, ast.Name) and node.id in BLOCKED_NAMES:
            raise ValueError(f"Name not allowed: {node.id}")

        # 3. Block attributes that start with "_" such as __class__,
        #    a common way to climb back to dangerous objects
        if isinstance(node, ast.Attribute) and node.attr.startswith("_"):
            raise ValueError(f"Attribute not allowed: {node.attr}")
  • ast.parse(code) turns the text into a tree. Invalid Python raises SyntaxError here, before anything runs.
  • ast.walk(tree) visits every node of the tree, every statement, name, call and attribute.
  • Rule 1 looks at ast.Import and ast.ImportFrom nodes. It takes the top-level module name, for example os from os.path. It rejects any name outside the allowlist.
  • Rule 2 looks at ast.Name nodes, the plain names in the code. A name from BLOCKED_NAMES raises ValueError.
  • Rule 3 looks at ast.Attribute nodes, the part after a dot. Any attribute that starts with an underscore is rejected. This closes the ().__class__ route of the section above.

Part 4Run the code in a separate, limited process

def run_code_safely(code: str) -> str:
    """Check the code, then run it in a separate, limited Python process
    and return what it printed."""

    try:
        check_code(code)
    except (SyntaxError, ValueError) as e:
        return f"Code rejected: {e}"

    # An empty temporary folder as the working directory
    with tempfile.TemporaryDirectory() as workdir:
        try:
            result = subprocess.run(
                [sys.executable, "-I", "-c", code],  # -I: isolated mode
                capture_output=True,                  # collect stdout and stderr
                text=True,
                timeout=TIMEOUT_SECONDS,              # stop endless loops
                cwd=workdir,                          # no access to our files by path
                env={},                               # no environment variables, no API keys
            )
        except subprocess.TimeoutExpired:
            return f"Code stopped after {TIMEOUT_SECONDS} seconds."

    if result.returncode != 0:
        return f"Code failed:\n{result.stderr.strip()}"

    return result.stdout
  • The function calls check_code() first. A SyntaxError or ValueError becomes the message "Code rejected", and nothing runs.
  • tempfile.TemporaryDirectory() creates an empty folder. The with block deletes it at the end.
  • [sys.executable, "-I", "-c", code] is the command line of the child. -c runs the code string. -I is isolated mode, which ignores environment variables of Python and the user's site packages.
  • capture_output=True collects what the child writes to stdout and stderr. Your own sys.stdout never changes, so the bug of Example 1 cannot happen here.
  • text=True returns that output as strings instead of bytes.
  • timeout=TIMEOUT_SECONDS stops the child after 5 seconds and raises subprocess.TimeoutExpired.
  • cwd=workdir starts the child in the empty folder. A relative path such as .env finds nothing there.
  • env={} gives the child no environment variables at all, so it cannot read your API keys from the environment.
  • result.returncode is 0 for a normal end. Any other value means an error, and the function returns the error text from stderr.

import ast
import re
import subprocess
import sys
import tempfile

from dotenv import load_dotenv
from langchain_google_genai import ChatGoogleGenerativeAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser


# Modules that a math answer may need. Everything else is rejected.
ALLOWED_IMPORTS = {"math", "statistics", "datetime"}

# Built-in names that a math answer never needs, but an attacker would.
BLOCKED_NAMES = {
    "open", "exec", "eval", "compile", "__import__", "input",
    "globals", "locals", "vars", "getattr", "setattr", "delattr",
    "breakpoint",
}

# Seconds before we stop the code (stops endless loops)
TIMEOUT_SECONDS = 5


def check_code(code: str) -> None:
    """Read the code as a syntax tree (without running it) and raise
    ValueError if it uses anything outside our small safe set."""

    tree = ast.parse(code)

    for node in ast.walk(tree):
        # 1. Only allow imports from the allowlist
        if isinstance(node, ast.Import):
            names = {alias.name.split(".")[0] for alias in node.names}
        elif isinstance(node, ast.ImportFrom):
            names = {(node.module or "").split(".")[0]}
        else:
            names = set()

        blocked = names - ALLOWED_IMPORTS
        if blocked:
            raise ValueError(f"Import not allowed: {', '.join(sorted(blocked))}")

        # 2. Block risky built-in functions such as open() or eval()
        if isinstance(node, ast.Name) and node.id in BLOCKED_NAMES:
            raise ValueError(f"Name not allowed: {node.id}")

        # 3. Block attributes that start with "_" such as __class__,
        #    a common way to climb back to dangerous objects
        if isinstance(node, ast.Attribute) and node.attr.startswith("_"):
            raise ValueError(f"Attribute not allowed: {node.attr}")


def run_code_safely(code: str) -> str:
    """Check the code, then run it in a separate, limited Python process
    and return what it printed."""

    try:
        check_code(code)
    except (SyntaxError, ValueError) as e:
        return f"Code rejected: {e}"

    # An empty temporary folder as the working directory
    with tempfile.TemporaryDirectory() as workdir:
        try:
            result = subprocess.run(
                [sys.executable, "-I", "-c", code],  # -I: isolated mode
                capture_output=True,                  # collect stdout and stderr
                text=True,
                timeout=TIMEOUT_SECONDS,              # stop endless loops
                cwd=workdir,                          # no access to our files by path
                env={},                               # no environment variables, no API keys
            )
        except subprocess.TimeoutExpired:
            return f"Code stopped after {TIMEOUT_SECONDS} seconds."

    if result.returncode != 0:
        return f"Code failed:\n{result.stderr.strip()}"

    return result.stdout


def extract_and_run_code(response: str) -> str:
    """Extract Python code from the response and run it safely."""

    # Find the fenced code block in the model's response
    code_match = re.search(r"```python\n(.*?)```", response, re.DOTALL)
    if not code_match:
        return f"No code found. Raw response:\n{response}"

    code = code_match.group(1)
    output = run_code_safely(code)
    return f"CODE:\n{code}\n\nOUTPUT:\n{output}"
