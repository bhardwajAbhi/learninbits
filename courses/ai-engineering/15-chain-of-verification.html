In one line

Chain of verification makes a model check each fact in its own answer and fix the wrong ones.

What you will learn

  • Why a fluent answer can still hold wrong facts
  • How to split a long answer into small facts that can each be checked
  • How four small chains work together, to write, list, check and fix
  • Why checking an answer with the same model is not always enough
  • What a check needs before you can trust its result

Read chapter 8 and chapter 14 first. This chapter builds chains of the same kind as chapter 8. It also asks the same question as chapter 14, namely when you can trust an answer from a model.

The idea

In chapter 14, you asked the model the same question several times and let the answers vote. A vote works well for one short answer, such as a number or a label. Many real questions need a long answer instead, such as a summary of a law or a report on a vulnerability. A long answer has no single value to vote on. It holds ten or twenty separate facts, and any one of them can be wrong.

A model writes such an answer in one smooth flow. Each sentence follows from the one before it, so a wrong date fits in as easily as a right one. When you ask the same model to check the whole answer, it reads its own text and usually finds it convincing.

Chain of verification (CoVe) breaks this flow into four steps. The model first writes an answer. Then it lists the facts in that answer, one per line. Next, it checks each fact on its own, without the rest of the answer around it. Last, it fixes every fact that failed the check. A small fact is easier to check than a whole answer, because the rest of the text cannot push the model toward a yes.

The method comes from research in 2023. The paper "Chain-of-Verification Reduces Hallucination in Large Language Models" by Dhuliawala and others at Meta showed fewer invented facts in long answers. The paper turns each fact into a short question, such as "When did the President sign the Act?", and answers each question in a fresh call. The code of this chapter uses a simpler version, which checks each fact directly.

Real-life analogy

A newspaper in Delhi prints a long story about a new law, say the DPDP Act. Before it goes to print, a fact-checker reads the story with a pencil. She circles every name, date and number, such as "11 August 2023" or "₹250 crore". Then she checks each circled item against the official text of the law. She does not ask whether the story sounds right, but whether each item is right. Chain of verification gives the model the job of that fact-checker.

The idea in one picture

The method runs four steps in a row. The output of each step is the input of the next one.

Chain of verification needs more calls to the model. An answer with 18 facts needs 21 calls, one for each fact and three more. The two examples show when this extra work helps.

What we build in this chapter

Both programs follow the same four steps, and each step has its own prompt. The first prompt writes the answer. The second lists the facts in that answer. The third checks one fact at a time. The fourth fixes the answer. Only the model and the question change between the two programs.

  • ChatGoogleGenerativeAI, ChatPromptTemplate and StrOutputParser are the model, the prompt and the parser of chapter 2.

Step 3Write the prompt for the first answer

    # Step 1 prompt: generate the initial response
    generate_prompt = ChatPromptTemplate.from_template("""
        Answer this question with specific facts and details:
        {question}
    """)
  • "Answer this question with specific facts and details" asks for a rich answer on purpose. A vague answer has few facts to check, and a detailed answer gives the later steps something to work on.

Step 4Write the prompt that lists the facts

    # Step 2 prompt: extract the claims
    extract_claims_prompt = ChatPromptTemplate.from_template("""
        Extract all specific factual claims from this text.
        List each claim on a separate line, numbered.
        Focus on dates, numbers, names and verifiable facts.

        TEXT:
        {response}

        FACTUAL CLAIMS:
    """)
  • "Extract all specific factual claims" turns the answer into a list of separate facts, which the code calls claims.
  • "List each claim on a separate line, numbered" fixes the format, so that your Python code can split the list at each line break.
  • "Focus on dates, numbers, names and verifiable facts" keeps the list to facts that a check can confirm or reject. An opinion such as "one of the strongest laws" cannot be checked, so it stays out.

Step 5Write the prompt that checks one fact

    # Step 3 prompt: verify one claim
    verify_prompt = ChatPromptTemplate.from_template("""
        Verify this specific claim. Is it accurate?

        CLAIM: {claim}

        Think carefully. If you are not certain, say "UNCERTAIN".
        Respond with exactly one of these:
        - VERIFIED: if you are confident the claim is correct
        - INCORRECT: <the correct information>, if you know the claim is wrong
        - UNCERTAIN: if you are not sure
    """)
  • The prompt holds one claim and nothing else. The first answer stays out, so the model cannot lean on the rest of its own text. This separation is the heart of the method.
  • "If you are not certain, say UNCERTAIN" gives the model an honest third option. Without it, a model tends to pick a side even when it does not know.
  • The three labels VERIFIED, INCORRECT and UNCERTAIN let your code decide what to do next. INCORRECT also asks for the correct information, so that the fix has something to work with.

Step 6Write the prompt that fixes the answer

    # Step 4 prompt: revise the response
    revise_prompt = ChatPromptTemplate.from_template("""
        Revise this response to fix any incorrect claims.

        ORIGINAL RESPONSE:
        {response}

        VERIFICATION RESULTS:
        {verification_results}

        REVISED RESPONSE (fix any incorrect claims, keep verified ones):
    """)
  • The prompt gives the model its first answer and all the check results together.
  • "Fix any incorrect claims, keep verified ones" asks for a careful edit, not a new answer. The parts that passed stay as they are.

Step 7Create the model and the four chains

def main():
    load_dotenv()

    # Initialize the model
    # Temperature 0 keeps the checks steady and repeatable.
    llm = ChatGoogleGenerativeAI(
        model="gemini-3.1-flash-lite",
        temperature=0,
    )

    # Parser to extract the text from the model response
    parser = StrOutputParser()
    # Create the four chains
    generate_chain = generate_prompt | llm | parser
    extract_chain = extract_claims_prompt | llm | parser
    verify_chain = verify_prompt | llm | parser
    revise_chain = revise_prompt | llm | parser
  • temperature=0 makes the model pick its most likely words. In chapter 14, you wanted different answers, so you raised the temperature. Here you want steady checks, so the same fact gets the same check result each time.
  • The four chains share one model and one parser. Each chain is the three-part chain of chapter 2, with its own prompt.

Step 8Write the first answer and list its facts

The function chain_of_verification() runs the four steps in order. Its first part writes the answer and turns the list of facts into a Python list.

def chain_of_verification(
    question: str,
    generate_chain,
    extract_chain,
    verify_chain,
    revise_chain,
) -> dict:
    """Run the full Chain of Verification pipeline."""

    # Step 1: Generate the initial response
    initial_response = generate_chain.invoke({"question": question})
    print("INITIAL RESPONSE:")
    print(initial_response)
    print("\n" + "-" * 40)

    # Step 2: Extract the claims, one per line
    claims_text = extract_chain.invoke({"response": initial_response})
    claims = [c.strip() for c in claims_text.strip().split("\n") if c.strip()]
    print("EXTRACTED CLAIMS:")
    for claim in claims:
        print(f"  {claim}")
    print("\n" + "-" * 40)
  • generate_chain.invoke({"question": question}) writes the first answer.
  • extract_chain.invoke({"response": initial_response}) returns the facts as one block of text.
  • claims_text.strip().split("\n") cuts that block at each line break, so that each line becomes one item of a list.
  • [c.strip() for c in ... if c.strip()] removes spaces at both ends of each line and drops empty lines. A model often leaves a blank line in a list, and an empty claim gives the check nothing to judge.

Step 9Check each fact on its own

    # Step 3: Verify each claim on its own
    verification_results = []
    print("VERIFICATION:")
    for claim in claims:
        result = verify_chain.invoke({"claim": claim})
        verification_results.append(f"{claim}\n  -> {result.strip()}")
        print(f"  {claim}")
        print(f"    -> {result.strip()}")
    print("\n" + "-" * 40)
  • The loop sends each claim to verify_chain in a separate call. Each call sees one claim only.
  • verification_results collects each claim together with its check result, so that the fix later sees both.
  • The program prints each result as it arrives, so that you can follow the checks one by one.

Step 10Decide whether to fix the answer

    # Step 4: Decide what to do, based on the verification results
    verification_text = "\n".join(verification_results)

    if "INCORRECT" in verification_text:
        # At least one claim is wrong, so rewrite the response
        final_response = revise_chain.invoke(
            {"response": initial_response, "verification_results": verification_text}
        )
        print("REVISED RESPONSE:")
        print(final_response)
    elif "UNCERTAIN" in verification_text:
        # Nothing is known to be wrong, but some claims could not be checked
        final_response = initial_response
        print("NO REVISION NEEDED - but some claims are UNCERTAIN")
        print("The initial response is kept, with unchecked claims in it.")
    else:
        # Every claim was verified
        final_response = initial_response
        print("NO REVISION NEEDED - All claims verified")

    return {
        "initial": initial_response,
        "claims": claims,
        "verifications": verification_results,
        "final": final_response,
    }
  • "\n".join(verification_results) joins all check results into one text.
  • if "INCORRECT" in verification_text looks for the word anywhere in that text. If it finds the word, the fix chain rewrites the answer.
  • elif "UNCERTAIN" in verification_text keeps the first answer, but the program warns you that some facts were not confirmed.
  • else keeps the first answer, because every fact passed.

The rule is short and easy to read. It also searches for a word anywhere in the text, not only in the label at the start of each result. A reply without any label, such as a question back to you, counts as nothing at all. The output below shows what this means in practice.

"""
Title: Chain of Verification Prompting (Google Generative AI)
Chain of Verification asks the model to write an answer, pull out the
facts it stated, check each fact on its own and then fix any fact found
to be wrong. Checking small facts one at a time is easier than judging
a whole answer at once.
uv run python src/14_chain_of_verification_google.py
"""

from dotenv import load_dotenv
from langchain_google_genai import ChatGoogleGenerativeAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser


def chain_of_verification(
    question: str,
    generate_chain,
    extract_chain,
    verify_chain,
    revise_chain,
) -> dict:
    """Run the full Chain of Verification pipeline."""

    # Step 1: Generate the initial response
    initial_response = generate_chain.invoke({"question": question})
    print("INITIAL RESPONSE:")
    print(initial_response)
    print("\n" + "-" * 40)

    # Step 2: Extract the claims, one per line
    claims_text = extract_chain.invoke({"response": initial_response})
    claims = [c.strip() for c in claims_text.strip().split("\n") if c.strip()]
    print("EXTRACTED CLAIMS:")
    for claim in claims:
        print(f"  {claim}")
    print("\n" + "-" * 40)

    # Step 3: Verify each claim on its own
    verification_results = []
    print("VERIFICATION:")
    for claim in claims:
        result = verify_chain.invoke({"claim": claim})
        verification_results.append(f"{claim}\n  -> {result.strip()}")
        print(f"  {claim}")
        print(f"    -> {result.strip()}")
    print("\n" + "-" * 40)

    # Step 4: Decide what to do, based on the verification results
    verification_text = "\n".join(verification_results)

    if "INCORRECT" in verification_text:
        # At least one claim is wrong, so rewrite the response
        final_response = revise_chain.invoke(
            {"response": initial_response, "verification_results": verification_text}
        )
        print("REVISED RESPONSE:")
        print(final_response)
    elif "UNCERTAIN" in verification_text:
        # Nothing is known to be wrong, but some claims could not be checked
        final_response = initial_response
        print("NO REVISION NEEDED - but some claims are UNCERTAIN")
        print("The initial response is kept, with unchecked claims in it.")
    else:
        # Every claim was verified
        final_response = initial_response
        print("NO REVISION NEEDED - All claims verified")

    return {
        "initial": initial_response,
        "claims": claims,
        "verifications": verification_results,
        "final": final_response,
    }


def main():
    load_dotenv()

    # Initialize the model
    # Temperature 0 keeps the checks steady and repeatable.
    llm = ChatGoogleGenerativeAI(
        model="gemini-3.1-flash-lite",
        temperature=0,
    )

    # Parser to extract the text from the model response
    parser = StrOutputParser()

    # Step 1 prompt: generate the initial response
    generate_prompt = ChatPromptTemplate.from_template("""
        Answer this question with specific facts and details:
        {question}
    """)

    # Step 2 prompt: extract the claims
    extract_claims_prompt = ChatPromptTemplate.from_template("""
        Extract all specific factual claims from this text.
        List each claim on a separate line, numbered.
        Focus on dates, numbers, names and verifiable facts.

        TEXT:
        {response}

        FACTUAL CLAIMS:
    """)

    # Step 3 prompt: verify one claim
    verify_prompt = ChatPromptTemplate.from_template("""
        Verify this specific claim. Is it accurate?

        CLAIM: {claim}

        Think carefully. If you are not certain, say "UNCERTAIN".
        Respond with exactly one of these:
        - VERIFIED: if you are confident the claim is correct
        - INCORRECT: <the correct information>, if you know the claim is wrong
        - UNCERTAIN: if you are not sure
    """)

    # Step 4 prompt: revise the response
    revise_prompt = ChatPromptTemplate.from_template("""
        Revise this response to fix any incorrect claims.

        ORIGINAL RESPONSE:
        {response}

        VERIFICATION RESULTS:
        {verification_results}

        REVISED RESPONSE (fix any incorrect claims, keep verified ones):
    """)

    # Create the four chains
    generate_chain = generate_prompt | llm | parser
    extract_chain = extract_claims_prompt | llm | parser
    verify_chain = verify_prompt | llm | parser
    revise_chain = revise_prompt | llm | parser

    # A question full of dates, numbers and names, so there is
    # more to check and more chance of a slip
    question = (
        "Tell me about India's Digital Personal Data Protection (DPDP) Act, "
        "2023: when it became law, who it applies to, the rights it gives "
        "people, and the penalties it sets."
    )

    print("=" * 60)
    print("QUESTION")
    print("=" * 60)
    print(f"\n{question}\n")
    print("=" * 60 + "\n")

    chain_of_verification(
        question, generate_chain, extract_chain, verify_chain, revise_chain
    )


if __name__ == "__main__":
    main()

What the two runs teach together

Put both runs side by side, and one pattern appears. In Example 1, the method made a mostly correct answer worse. In Example 2, it found the one real error but did not fix it. Neither run ended with a better answer than the first one. This is not a bug in your code, and it does not make the method useless. It shows the condition that the method depends on.

The check did several things well. Stable, well-known facts passed, such as a CVE number or the name of a law. Checking one fact at a time found an error that a reading of the whole answer can miss. The list of facts also made every claim visible. Even when the check fails, a person can now see exactly what the answer says and check it quickly.

What the check needs is a source that knows more than the writer. Here, the checker was the same model, with the same memory that wrote the answer. When that memory holds a wrong fact, the check confirms it. When the memory is unsure, the check can turn a right fact into a wrong one. A fact that changes over time also needs a source with a date. You can trust a check that names a source, such as the text of the Act, far more than a check from memory.

The paper behind the method points the same way. It asks each verification question in a fresh call, so that the first answer cannot steer the check. It also reports that the method reduces invented facts but does not remove them. Later chapters of this course give the check a real source. Retrieval in chapter 34 gives the model documents to check against. Tools in chapter 40 let it look up a fact instead of recalling it.

When it works and when it does not

  • It works when the checker knows more than the writer, or has a source. Examples are a stronger model as the checker, a check against search results or a check against the official text.
  • It helps even without a source, when a long answer mixes well-known facts with a few rare ones. The well-known facts pass, and the list shows the rest for a person to check.
  • It does not help when the writer and the checker share the same gaps in knowledge. Both runs of this chapter showed this.
  • It costs more. Suppose one call costs ₹0.40. An answer with 18 facts then costs about ₹8.40, compared with ₹0.40 for the first answer alone. For 1 lakh questions a month, that is ₹8.4 lakh instead of ₹40,000.
  • It cannot know today's facts. A check against memory confirms what was true in the training data, not what is true now.
  • It can lose context. A fact without its subject gets no real check result.

Security lens

In security work, a wrong fact is a risk, not only a mistake. The first answer of Example 2 said that all versions before 1.0.1g contained Heartbleed. A team that believes this can waste effort on old servers that never contained the bug. The correction of the check, "prior to 1.0.1f", is worse. It suggests that version 1.0.1f was safe, so a team can leave a vulnerable server unpatched.

  • Never take versions, CVE details or fixes from the memory of a model. Check them in the National Vulnerability Database (NVD) or in the advisory of the vendor.
  • Read "verified" as "consistent with the memory of the model". It is not a guarantee, and it carries no date.
  • Keep the facts and their check results in the report. A reviewer can then see which facts were checked and how, instead of trusting a polished final text.
  • The same holds for law. Penalty amounts and deadlines come from the official text of the Act and the Rules. A summary from a model is only a starting point.

Check yourself

Why does the check prompt hold one fact and not the whole answer?

So that the rest of the answer cannot push the model toward a yes. Each fact is judged alone, which makes a wrong fact easier to notice.

In Example 1, the check asked "Which Act?" for four facts. What caused this, and what is the fix?

The facts said only "The Act", without the name of the law. The check saw each fact alone and could not tell which Act it meant. The fix is to ask for facts that each name their subject.

The check marked "As of mid-2024, the rules are still being prepared" as VERIFIED. Why is that not enough?

The check compares the fact with the memory of the model, which stops at its training data. The DPDP Rules came out in November 2025, so the fact is out of date. A fact that changes over time needs a source with a date.

Key terms at a glance

TermMeaning
Chain of verification (CoVe)A prompting method that writes an answer, checks its facts one by one and fixes the wrong ones.
ClaimOne fact from an answer, small enough to check on its own.
