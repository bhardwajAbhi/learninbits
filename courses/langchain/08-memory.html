In one line

A chat history sends the earlier messages with each new question, so that the model can answer follow-up questions in a conversation.

What you will learn

  • Why a model forgets each question, and how a chat history fixes that
  • How to build a chat prompt with a system message, a place for the history and the new question
  • How LangChain keeps and adds the history for you
  • How to build a chat page that shows each answer while the model writes it

Read chapter 6 first, because this chapter uses a chain. Chapter 4 explains the reruns of Streamlit.

The idea

A model has no memory. Each call starts fresh, and the model sees only what that call sends. If the user asks "What is a dangerous permission?" and then "Give me two examples of it", the second call does not know what "it" means.

A chat history fixes this. The app keeps every question and every answer. With each new question, it sends the earlier messages too, so that the model can read the whole conversation. The model still has no memory, but each call now carries the context that it needs.

Streamlit adds one more problem. It runs the whole script again after each action, so a normal Python list starts empty each time. Streamlit keeps data between reruns in session state, a store that lasts while the browser tab is open. LangChain can keep the history there.

Real-life analogy

Think of a support desk where a different person answers each call. If the notes of earlier calls are attached to each new call, the person can continue where the last one stopped. Without the notes, the caller must explain everything again.

What you will build

You will build two pages from the same chain. The first page shows the answer and, below it, the full history, so that you can see what the model receives. The second page is a chat window, like the apps that you already know, and it shows each answer while the model writes it.

Build the history page

Step 1Create the file

In the code folder, create the folder 08_adding_memory and in it the file chat_history_example.py.

Step 2Import the libraries

from langchain_ollama.chat_models import ChatOllama

# Adding history / memory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_community.chat_message_histories import StreamlitChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

from langchain_core.globals import set_debug
import streamlit as st
  • ChatPromptTemplate makes a template from a list of messages, each with a role, such as system or human.
  • MessagesPlaceholder marks the place in the template where the history goes.
  • StreamlitChatMessageHistory keeps the messages in the session state of Streamlit, so that they survive each rerun.
  • RunnableWithMessageHistory wraps a chain. It adds the history before each call and saves the new messages after it.

Step 3Load the model and write the chat prompt

set_debug(True)

llm = ChatOllama(model="gemma:2b")

prompt = ChatPromptTemplate.from_messages(
    [
        (
        "system",
            """
            You are an Android Security and Secure Coding Assistant.

            You help developers understand:
            - Android Security
            - Secure Coding Practices
            - Android Internals
            - Android Security Model
            - Mobile Malware
            - OWASP Mobile Top 10
            - Privacy
            - Reverse Engineering
            - Android Architecture

            Use the previous conversation to understand follow-up questions.

            Keep your answers concise and technical.
            """
        ),
        MessagesPlaceholder(variable_name="chat_history"),
        ("human", "{input}")
    ]
)
  • The system message gives the model its role and the topics that it covers. It is the same in every call, so that the assistant keeps one style.
  • "Use the previous conversation to understand follow-up questions." tells the model why the history is there.
  • MessagesPlaceholder(variable_name="chat_history") is the place for the earlier messages. The name must match history_messages_key in the next step.
  • ("human", "{input}") is the new question. Its slot name must match input_messages_key.

Step 4Wrap the chain with the history

chain = prompt | llm

history = StreamlitChatMessageHistory()

chat_with_history = RunnableWithMessageHistory(
    chain, 
    lambda session_id:history,
    history_messages_key="chat_history",
    input_messages_key="input",
)
  • chain = prompt | llm is a normal chain, as in chapter 6.
  • StreamlitChatMessageHistory() creates the history. It keeps the messages under the key langchain_messages in the session state.
  • lambda session_id: history tells the wrapper which history to use for a session. This app has one user, so it always returns the same history.
  • history_messages_key and input_messages_key connect the wrapper to the two slots of the template.

Step 5Build the page

st.set_page_config(page_title="Android Security Assistant")

st.title("Android Security Assistant")

col1, col2 = st.columns([6, 1])

with col1:
    question = st.text_input(
        label="Ask a question",
        label_visibility="collapsed",
        placeholder="Ask anything about Android security..."
    )

with col2:
    ask_button = st.button(label="Send", use_container_width=True)
  • st.columns([6, 1]) splits the row into two columns, a wide one for the text box and a narrow one for the button.
  • label_visibility="collapsed" hides the label of the text box, so that the row looks like a search bar.

Step 6Ask the question and show the history

if ask_button and question.strip():
    with st.spinner("Thinking..."):
        response = chat_with_history.invoke(
            {"input": question},
            config={"configurable": {"session_id": "any"}}
        )
    
    st.subheader("Answer")
    st.success(response.content)
    st.divider()

    # Chat history
    st.subheader("History")
    for message in st.session_state["langchain_messages"]:
        if message.type == "human":
            st.warning("Question: " + message.content)
        else:
            st.info("Answer: " + message.content)
        
    st.divider()
  • config={"configurable": {"session_id": "any"}} names the session. The wrapper passes this name to the lambda from Step 4.
  • st.success shows the answer in a green box.
  • The loop reads st.session_state["langchain_messages"] and shows each message. Questions appear in yellow boxes and answers in blue boxes, so that you can see the full history.

Turn it into a chat page

The second file uses the same imports, template and wrapper. Only the page changes. Create app_ollama.py in the same folder and copy Steps 2 to 4 into it. Then add the page below.

Step 7Show the earlier messages as chat bubbles

st.set_page_config(page_title="Android Security Assistant")

st.title("Android Security Assistant")

st.caption(
    "Ask questions about Android Security, Secure Coding, Android Internals, "
    "OWASP Mobile Top 10, Malware Analysis, Privacy and Reverse Engineering."
)

# ----------------------------------------------------------
# Display Previous Conversation
# ----------------------------------------------------------
for message in st.session_state["langchain_messages"]:

    role = "user" if message.type == "human" else "assistant"

    with st.chat_message(role):
        st.markdown(message.content)
  • st.caption shows a short line in gray below the title.
  • The loop runs at the start of each rerun and draws all earlier messages again. Without it, the old messages disappear after each question.
  • st.chat_message(role) draws a chat bubble with an icon for the user or the assistant.

Step 8Read the question and stream the answer

question = st.chat_input(
    "Ask anything about Android Security..."
)

if question:

    with st.chat_message("user"):
        st.markdown(question)

    with st.chat_message("assistant"):

        with st.spinner("Thinking..."):

            response = chat_with_history.stream(
                {"input": question},
                config={
                    "configurable": {
                        "session_id": "any"
                    }
                },
            )

            st.write_stream(response)
  • st.chat_input shows a chat box at the bottom of the page. It returns the text after the user presses Enter.
  • The question appears in a user bubble at once, so that the user sees it while the model works.
  • chat_with_history.stream(...) works like invoke(), but returns the answer in small pieces while the model writes them.
  • st.write_stream(response) shows each piece as it arrives, so that the user starts reading at once. In chapter 4, the user waited for the full answer.

Your output can be different

A language model does not always give the same answer. Your examples can be other permissions. The follow-up question will still work, because the history carries the first question.

Look closely

In both runs, the model understood "it" in the second question and answered about dangerous permissions. That is the history at work.

The facts are less reliable. The first page says that READ_PHONE_STATE gives access to the battery level and can take screenshots, which is not what that permission does. The model also defines a dangerous permission as one that gives "more access than necessary". On Android, a dangerous permission is one that protects private data, such as the camera or contacts, so the system asks the user first. A history makes a conversation possible, but it does not make a small model correct.

Security lens

The history keeps everything that the user typed, including secrets, such as a password pasted by mistake, and sends it with every later question. The session state lasts while the tab is open, so close the tab or reload the page to clear it. This app also uses one fixed session name, "any". In an app with many users, each user needs their own session name, or one user could read the history of another. Finally, the history grows with each message, so each call becomes slower and, with a cloud model, more expensive.

Check yourself

Why does the second question fail without a history?

Each call starts fresh, so the model does not know what "it" refers to.

Why does the app keep the history in the session state and not in a normal list?

Streamlit runs the whole script again after each action, so a normal list starts empty. The session state keeps data between reruns.

What is the difference between invoke() and stream()?

invoke() returns the full answer at the end. stream() returns the answer in pieces while the model writes it.
